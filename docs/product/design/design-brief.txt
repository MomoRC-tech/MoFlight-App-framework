## Current visual direction

Preserve the compact aviation interface: deep navy canvas and layered dark cards, blue/cyan actions and selection, warm orange paper-logbook actions, purple assistant accents, readable light text and licensed photographic headers with dark overlays. Group related content with a clear title, primary value/action and quieter supporting information. Use the approved reference's asymmetric dashboard composition and restrained spacing; adapt it to available width and enlarged text.

Keep German labels beside important navigation/status symbols. Show saved facts and explicit unknown/unavailable states. Decorative photographs and illustrative design examples do not establish weather, tracks, source freshness or copied paper entries.

## Authority and scope

1. The [approved four-screen image](../design-sources/2026-10-16-four-screen/reference.png) controls baseline layout, cards, colors, buttons and spacing. Its sample data is illustrative; see its [source record](../design-sources/2026-10-16-four-screen/README.md).
2. The [17 October shell corrections](../2026-10-17-native-shell-corrections.md) amend that baseline with Übersicht, Flüge, Flugbuch, Verein and AI; the compact fixed branded/profile header; and aircraft-share rings.
3. The [18 October header decisions](../2026-10-18-header-status-review.md#package-1b-decision-checkpoint) amend their scope with aircraft B, contextual app Back, separate provider-history Back/Close and Connection → Med → Profile. Med reads unbekannt and opens a read-only explanation.
4. This handbook consolidates those decisions. Earlier prototype choices apply only where explicitly carried forward. Code values record implementation and cannot approve an unresolved visual difference.

Manuel owns design decisions. Priorities, journeys and account/book behavior remain in the [project plan](../../project-plan.md), [journey map](../2026-10-13-journey-information-map.md) and feature contracts. Link those contracts rather than duplicating them here.

## Status vocabulary

Keep **decision status** (approved, proposed, superseded), **implementation status** (implemented, partial, absent) and **verification status** (checked for a named source/platform, pending, unavailable) separate. An approved design can have an implementation gap; a current code value need not be an individually approved token; a browser example is not native acceptance.

## How to change the design

1. Capture scope/acceptance in the matching GitHub Issue. Edit the relevant chapter and prepare a concrete example/diff, naming affected components, symbol IDs, states and widths.
2. Obtain Manuel's choice where a new appearance/behavior needs a decision. Record owner/date, rationale and exactly what it supersedes in [history](history.md).
3. Implement the approved scope through shared styles/components where appropriate, preserving data/unknown rules. Code-token centralization remains a [separate proposed improvement, #24](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/24).
4. Run `python scripts/design_handbook.py`, then `python scripts/design_handbook.py --check`. Apply the [verification workflow](../../development/verification-workflow.md) to the actual change: documentation checks for documentation; applicable source/platform checks for changed native UI.

Markdown chapters, [color-roles.json](color-roles.json), [symbols.json](symbols.json), the component illustrations and HTML template are maintained inputs in this directory. Color-role metadata controls semantic usage; source code supplies implemented values. The implementation inventory, HTML guide, plain-text brief and compatibility symbol HTML are generated outputs. Do not hand-edit a generated palette or maintain a second catalogue. Original assets retain their locations/licenses.

The generator uses Python's standard library and repository files only: no network, installs, model calls or app builds. Supported chapter Markdown includes headings, paragraphs, links/images, emphasis, lists, tables and fenced code; unsupported raw HTML is rejected. Examples are assembled from the maintained catalogue/template.

## Charts and missing values

[season-model.ts](../../../apps/platform-lab/src/mobile/season-model.ts) uses `#46ccff`, `#48dba5`, `#3595fe`, `#a794ff`, `#f9b65b`, `#f48bb4`. Registration determines stable color across count/time distributions. Colors can repeat, so names, counts, known time and accessible descriptions identify aircraft. These colors do not mean warnings, freshness or goal progress.

Zero and unknown differ. Missing duration contributes no known minutes and retains its unknown notice. Missing distance/weather stays — with context. Do not fill empty panels with illustrative measurements.

## Symbol ownership

The [51-entry catalogue](../symbol-reference.html) is the detailed meaning/function reference. [symbols.json](symbols.json) is its maintained source; both the compatibility catalogue and combined guide are generated from it. Keep N/H/S/D/K/A/T/X/B identifiers stable during redesigns.

Separate semantic roles even when characters repeat: a right arrow can mean route direction, continue or login required; a tick can mean selected book or previous session confirmation. Assess artwork size, optical balance, stroke and effective touch area separately.

## Header, overlays and navigation

Keep header/navigation outside the scrolling canvas. Header order is logo/title, Connection → Med → Profile. Truncate title before shrinking controls. Current font scale above 1.3 places controls on a second wrapping row; subtitle renders only at width at least 412 with normal text.

App overlays/details replace logo with contextual Back and expose one active accessible header. Return through nested overlays to prior page/filter/scroll state. A different book invalidates old flight-detail history. Medical opens a read-only unknown-record explanation.

Provider Close, connection status and origin belong to its app-owned toolbar. Provider-history Back affects the original embedded webpage; Close returns to MoFlight without promising logout. Preserve retained browser parent, busy/recovery guards and provenance. OS-owned full-screen surfaces keep their own controls. See [header decisions](../2026-10-18-header-status-review.md#package-1b-decision-checkpoint).

Bottom navigation has five equal icon/label destinations and semantic selected state. Current code hides it with the AI keyboard and app/provider overlays. Do not reintroduce an old floating dock or add a destination through documentation cleanup.

## Responsive layout and text

| Level | Visual question / current reference |
| --- | --- |
| MIN, 360 dp | Check overlap, clipping, scrolling and keyboard. Enlarged text avoids forced compact pairings. |
| MAIN, 390–412 dp | Primary fidelity target for approved geometry, spacing, colors and hierarchy. Code values alone do not prove it. |
| MAX, 600+ dp | Bound forms/details/card groups or use columns/master-detail. Current shell uses 600/960 bounds; forms commonly 480/520; dashboard groups cap at 430 and use two columns at width 840 when text is not enlarged. |
| Large text / landscape | Controls grow, labels remain, content reflows with keyboard/insets. Above font scale 1.3 several sections stack; rings hide if values/text cannot fit. |

At 600+ dp—including landscape phones, tablets/foldables—cap and center individual groups or use an appropriate multi-column composition. A 480 dp cap is illustrative, not universal. Record actual logical dp, density and font scale. The [refinement policy](../2026-10-16-ui-fidelity-refinement.md) controls acceptance.

Respect safe areas/system bars. Current AI layout accounts for keyboard overlap, keeps the multiline composer reachable and preserves drafts on unavailable service/retry. Browser specimens do not prove native keyboard behavior.

## Honest data and state presentation

- Provider tick: previous matching check, not continuing login, imported-data freshness or cloud sync.
- Med / unbekannt: unknown until separate source/input work exists; no prototype expiry date or invented fit-to-fly status.
- Rings: aircraft shares of count/known minutes; no unstated goal or missing-time-as-zero. Native rings do not open the old inline-breakdown prototype.
- No-track: missing track evidence; no decorative measured route. Cloud/weather and club photographs are category/decorative elements.
- Preserve clear empty/error/retry wording, scoped selection and pending work. Simplification must not hide required ownership/recovery/confirmation decisions.

## Accessibility and acceptance

Retain visible labels, button/tab roles, selected/expanded/busy/disabled states and specific action names. Decorative submarks must not duplicate controls. Unknown/error meanings need text or shapes as well as color.

When affected, check actual touch regions, reading/focus order, long labels, text scaling, contrast over the displayed photo crop and keyboard reachability. Some small faces/targets and universal focus styling remain [review gaps](history.md). Spoken TalkBack/focus, iOS, physical-device and positive provider-history checks remain separate from bounded Android evidence.

Follow the [verification workflow](../../development/verification-workflow.md): this consolidation adds no native acceptance. Substantial UI changes need their relevant committed-source Release/native matrix; logic-only changes do not trigger unrelated visual audits.
