## Status vocabulary

Keep **decision status** (approved, proposed, superseded), **implementation status** (implemented, partial, absent) and **verification status** (checked for a named source/platform, pending, unavailable) separate. An approved design can have an implementation gap; a current code value need not be an individually approved token; a browser example is not native acceptance.

## How to change the design

1. Capture scope/acceptance in the matching GitHub Issue. Edit the relevant chapter and prepare a concrete example/diff, naming affected components, symbol IDs, states and widths.
2. Obtain Manuel's choice where a new appearance/behavior needs a decision. Record owner/date, rationale and exactly what it supersedes in [history](history.md).
3. Implement the approved scope through shared styles/components where appropriate, preserving data/unknown rules. Code-token centralization remains a [separate proposed improvement, #24](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/24).
4. Run `python scripts/design_handbook.py`, then `python scripts/design_handbook.py --check`. Apply the [verification workflow](../../development/verification-workflow.md) to the actual change: documentation checks for documentation; applicable source/platform checks for changed native UI.

Markdown chapters, [color-roles.json](color-roles.json), [symbols.json](symbols.json), the component illustrations and HTML template are maintained inputs in this directory. Color-role metadata controls semantic usage; source code supplies implemented values. The implementation inventory, HTML guide, plain-text brief and compatibility symbol HTML are generated outputs. Do not hand-edit a generated palette or maintain a second catalogue. Original assets retain their locations/licenses.

The generator uses Python's standard library and repository files only: no network, installs, model calls or app builds. Supported chapter Markdown includes headings, paragraphs, links/images, emphasis, lists, tables and fenced code; unsupported raw HTML is rejected. Examples are assembled from the maintained catalogue/template.

## Review and design response

The baseline makes too many elements equally prominent: tiny header title beside three status controls, gradient cards around every group, dense flight metadata before results, and charts mixed with everyday tasks. The alternative establishes a reading order: destination → essential actions → flight information → optional detail.

- **Foundation:** matte navy canvas `#0b141c`, opaque panels `#14232f`, raised controls `#1d3242`, high-contrast off-white text, muted blue-grey labels and mint action color `#76dfc6`. Preserve the selected duotone art and Thermik logo. No external fonts. The later ASK-21 header refinement uses an original generated raster scene; icon/logo assets stay unchanged.
- **Typography and spacing:** 15/22 body, 19/26 section headings, 28/34 header title and 18/24 ring-adjacent season values. Shared cards use 18-unit padding and 22-unit corners; the dense season card uses 14-unit padding. Page spacing is 18. Primary actions are at least 52 units, labelled icon targets at least 48. Text follows system scaling.
- **Header (C05/C06):** realistic ASK-21-like soaring scene with restrained relative-airflow illustration over navy, 46-unit unchanged Thermik logo, destination title and labelled Data/Medical/Profile controls. All three controls use the existing 28-unit duotone symbols and card surface/radius14; status color belongs to the age/date caption, not a frame. Phones place controls below the destination; wide layouts share one row and enlarged text wraps. Keep the header no taller than the preceding APK at matching viewport/font settings. Header-only update/login admission remains unchanged.
- **Start — revised after Manuel's feedback:** remove the permanent leading connection/reminder box. Meine Saison is the first content group, with a small flight illustration and one latest saved, dated flight integrated into the same card. Prioritize calendar date/relative age (for example −4 Tage or −2 Wochen), recorded PIC and aircraft. Do not infer PIC from another crew slot. Its row opens the exact saved flight; Alle Flüge ansehen opens the general list. Unknown dates/times and ambiguous same-day chronology remain explicit.
- **Season comparison:** four compact aircraft-split rings: known reported time and starts for each of the current/prior calendar years. Aircraft colors stay stable across measures/years and have a shared registration legend. Empty/unknown time has no fabricated arc. Ring values sit beside the artwork so enlarged text can grow; the measure pair stacks at enlarged text. These are saved-year totals, not a claim of complete coverage or equal year-to-date periods.
- **Statistics overlay (C20):** the overview includes one current/prior-year monthly chart with Flüge/Flugstunden chips. Jan–Dec occupy one row; all twelve months fit visibly without horizontal scrolling, including enlarged text. Only compact month/marker labels cap font scaling at 1; surrounding controls/captions scale. Preserve year labels, unknown/partial markers, equal current-month cutoffs and blank future months. Chart filters and contributor drilldown perform no provider work.
- **Flüge (C04/C09):** prominent search, year chips, aircraft filter, concise saved-row count, optional coverage disclosure. Clear search without clearing the year, or reset all filters with one action. The list shows date, reported time, registration, model and route. Details lead with aircraft and duration, with complete original evidence below. No inferred route, track, role or flight time.
- **Navigation (C07):** five preserved destinations, selected filled tile and heavier mint label. Enlarged text uses wrapped rows. The footer identifies this as a development version; the synthetic preview remains under Development.
- **Empty/deferred states:** explain the next supported step. Paper setup stays “In Vorbereitung”; AI explains its synthetic example scope. A compact Meine Saison empty/error state gives passive guidance to the header Daten action without invented totals or the removed permanent connection box.
- **Responsive composition:** bounded single groups through phone/tablet widths; at 840+ a two-column Start. Flight rows use two columns at 600+ with standard font scale. The month canvas remains a single row at every width; all twelve months fit visibly at enlarged text too, using compact axis labels. Both series retain year-labelled legends and unknown/partial markers.

### Header artwork generation prompt

Built-in image tool, opaque background, original PNG2172×724 (measured file dimensions); no API/CLI fallback or private image input. Final prompt:

> Use case: photorealistic-natural. Asset type: extremely wide, low-height banner background for a compact dark navy personal sailplane flight-log app header. Generate a new original, highly realistic aviation photograph/visualization, landscape aspect ratio 3:1, approximately 1536 x 512. No text, no logos, no frame, no UI. Scene: a white fiberglass Schleicher ASK-21-like two-seat training sailplane genuinely soaring in a gentle coordinated bank above hazy forested hills, seen from a nearby aircraft, slightly above and ahead of its left side. Accurate recognizable ASK-21 proportions: substantial rounded tandem two-seat nose, long clearly divided two-piece canopy, mid-mounted long straight double-tapered wings with blunt simple tips and NO winglets, slender rear fuselage, proper vertical fin with T-tail horizontal stabilizer. Small red-orange nose/wingtip safety accents. Not a generic extreme racing glider, not a jet, not a toy, no propeller, no steep aerobatics. Composition critical: place the complete aircraft exclusively in the RIGHT HALF of the wide image, wingspan about 40 percent of canvas width; fuselage diagonally nose toward lower-left, tail upper-right, wings foreshortened naturally. Aircraft must read at a very small UI size. Keep the LEFT 45 percent mostly clean, very dark navy #0b141c with a gentle atmospheric fade for a separate existing logo and screen title; keep bottom 25 percent dark and quiet for separate controls. Cool blue hour, realistic white fiberglass reflections and translucent smoky canopy, subtle terrain far below to establish a believable in-flight situation. Add just 4 to 6 fine semi-transparent cyan-white aerodynamic visualization streamlines following the SAME local relative-wind direction from ahead of nose past wings toward the tail and downstream; they should gently deflect around the aircraft and indicate a restrained downstream wingtip wake. Thin, elegant, physically coherent, no big random crossing swooshes, no neon ribbons, no contrails or smoke. These are illustrative airflow overlays, not literal visible wind or CFD evidence. Photographic realism with understated airflow graphics. Preserve quiet navy background and complete aircraft visibility.

The shell retains Start and its processed selectors across ordinary tab navigation. Unchanged view inputs reuse summary/month calculations; returning to Start does not itself read the library. Duplicate native active notifications no longer trigger another read. Real background/foreground transitions and provider closure still perform guarded local revalidation. The app-switch correction retains the last verified screen and completed detail during ordinary quiet revalidation; equal results reuse references, changed evidence invalidates detail, and missing/failed validation removes retained data. Provider/writer admission clears retained data through the active boundary; changed owners never reuse prior data. No persistent unscoped cache or generation-only shortcut was introduced. Host regressions cover these boundaries; they do not establish that the full user-reported reload symptom has been reproduced or eliminated on a device.
