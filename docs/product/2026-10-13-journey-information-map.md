## Single-action login and flight loading — 21 October 2026

**Selected user need, Manuel:** menus are too complex. Users should open the app, use one login action and immediately retrieve their data, with no or minimal curation. This refines the next implementation package under [#22](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/22); it supersedes the earlier normal-journey requirement for separate retrieval/review/save actions. Manuel subsequently authorized implementation on 21 October; the combined flow is implemented in source. [Verification and remaining native/provider acceptance](../verification/2026-10-21-simple-flight-loading.md) remain separate.

- **First use:** one primary **Mit Vereinsflieger anmelden & Flüge laden** action, with concise source/local-storage information before credentials. Complete provider-required login on the original page; continue through verified own-flight retrieval, deterministic assessment and local saving, then show usable flights/Start. Necessary fresh local storage is internal setup, not a user-facing library-creation task. No book is required.
- **Returning use:** saved flights open locally and offline. **Flüge aktualisieren** reuses a retained session when verified; request login only when necessary. The initiating action requests the complete foreground retrieval/save sequence, not retrieval on every app open, background scheduling or polling.
- **Minimal curation:** valid provider-backed records save without routine row review or a separate save click. Deterministic validation, provider authority, account scoping, original evidence/revisions, deduplication and recovery still apply. Missing optional values remain unknown; ambiguous observations remain preserved separately rather than silently accepted. Ask only where unresolved account association, unexpected switching, identity ambiguity or unsafe recovery needs an actual decision. Do not require manual reconciliation of provider durations against clock subtraction. Save safe independent records where supported, with a truthful unresolved-item summary.
- **Simple progress and result:** Anmelden → Flüge laden → Speichern, followed by a short new/updated count, covered period and any unresolved items. Saved-data freshness advances only after confirmed saving. Failed/cancelled work preserves existing flights; retry must avoid duplicates. Profile remains the administrative home, with technical details secondary.
- **Defaults and boundaries:** reuse approved #19 first-retrieval/current update windows; custom periods remain secondary and bounded retrieval does not imply lifetime completeness. Own flights only; no book/paper integration, other source categories, provider writes, credential-policy changes, cloud/AI or paid services. Preserve existing approved appearance/navigation.

**Acceptance:** a fresh zero-book user reaches saved own flights using the single initiating action plus provider-required login; a verified returning session avoids repeated login and routine review/save prompts. Cover expired/wrong accounts and foreign IDs, partial/empty/unknown/conflicting records, cancellation, uncertain/failed save, idempotent retry and actual offline restart. Check affected Android small-width, enlarged-text, keyboard and TalkBack behavior. Define safe automatic-save admission and any unavoidable first-account confirmation in the implementation contract; retain source/owner/recovery guards. Host/synthetic, live-provider and native evidence remain distinct. The earlier multi-step flow does not establish this acceptance; use the source-specific package evidence.
