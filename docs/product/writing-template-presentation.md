## Required outcome

Updated product intent (Manuel, 2026-10-13): [the consolidated journey](2026-10-13-journey-information-map.md#catch-up-on-the-paper-logbook) requires both phone-side instructions and a printable sheet from the same reviewed snapshot, suggests a batch completing the next physical page with adjustment, and replaces mandatory copied-entry confirmation with assumed written progress checked at the next session. Existing lab evidence above still describes the old explicit-confirmation implementation.

The pilot can see exact entries to copy without reconstructing them from a comparison report. Correctness, placement and readability are required. Phone and printable outputs use one persisted resolved snapshot. Printable output is desired product scope; PDF, HTML or another concrete file/rendering technology is not selected. The current roadmap retains later writing implementation and its gates.

## Content and interaction contract

- Bind the complete view to one immutable resolved snapshot with source, decision, calculation and presentation/rules versions. Reopen it after offline restart. Reconciliation changes create a new revision; do not silently mix new values into instructions while the pilot is copying them.
- Identify the target book/layout and continuation page, row and destination field for every new value. For the supported prototype book, continue the current ten-row page before opening the next. Screen dimensions need not imitate a 420 x 148 mm PDF spread.
- Show exact numbering, dates, aircraft, registration, launch information, crew/roles, durations, remarks and required carryovers/page totals according to the supported layout and resolved rules. Show units and the established time basis; use deterministic calculations. Distinguish intentional blanks from unreadable/unknown values. Required unknowns trigger feedback before the affected instructions become ready.
- Separate already-written context from new values to copy with text/symbols as well as visual treatment. A narrow-screen row or field view is acceptable if destinations remain clear. Text must be legible, unclipped and navigable without guessing which column it belongs to.
- Keep findings, provenance and explanations accessible beside the template. Clearly separate these from literal writing instructions; include report text in a paper remarks field only when it is explicitly part of the resolved entry.
- Trigger selected by Manuel, 18 October 2026: start assumed written progress for the selected entries/revision when the user opens the final writing instructions or successfully saves/shares the printable sheet. Previewing and adjusting the batch does not advance progress. No completion prompt; never treat the assumption as confirmed paper evidence. Preserve the last confirmed anchor; almost always check the remembered last entry's number/details at the next session, otherwise accept the actual last written flight number for the named book. Resolve it against book-scoped entries/snapshots; unknown/ambiguous numbers or missing required continuation values need targeted details or a photo (Manuel, 18 October 2026). Reopening/downloading/printing the same snapshot cannot repeatedly advance assumptions. Cancellation/retry and partial/no-writing recovery remain contract work ([state semantics](flight-logbook-state-and-queries.md), [#7](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/7)).
- Preserve older snapshots and decisions. Show when newer evidence requires review; never silently rewrite an old template. Required printable output and any optional additional export formats use the same snapshot and agree with every copyable value/destination.
- Keep local presentation and stored inputs private to the selected dataset/profile. Later cloud/account integration applies the independent ownership and negative-access gates. In-app presentation requires no export worker.

## Acceptance evidence to collect

| Scenario | Expected evidence |
| --- | --- |
| T01 Continued page | Start at number 69/row 9; show 70 in row 10 and 71 on the next page, with independently verified roles/carryovers/totals and existing context clearly identified. |
| T02 Readability and unknowns | On supported Android/iOS screens, every destination and value is readable; no color-only distinction. An unknown required value requests feedback rather than inventing writing instructions. |
| T03 Resume and paper-state check | Preview/adjustment leaves progress unchanged; opening final instructions or successfully saving/sharing the printable sheet creates the revision-linked assumption while confirmed evidence stays unchanged. Reopen/export the same snapshot offline without duplicating advancement. Next-session confirmation, entry of the actual last written book number or a needed photo reconciles unwritten/partial batches, preserving old revisions and historical gaps. Verify known partial/no-writing stopping points and unknown/ambiguous/foreign-book numbers without inventing paper values. Cancellation/retry acceptance needs its remaining contract. |
| T04 Phone/print parity | Compare every copyable field/destination with the same reviewed snapshot; verify selected printing/export runtime and legibility. Both outputs are requested; a bounded phone-only trial must not claim acceptance of both. No concrete file format is selected. |

These are proposed acceptance criteria. No app view, renderer, offline device test or optional export has been implemented or tested by this documentation change. Prototype instruction/rule snapshots remain historical sources; current generator code reuse remains unverified.
