## Proposed reconciliation behavior

1. Bind the local dataset to verified source account/club references. A mismatch stops import and preserves existing data. Display names are not identity keys.
2. Stage and validate one complete bounded window before proposing any writes. Interrupted results may retain raw observations, but cannot advance verified coverage. Complete individual windows may later accumulate while other history gaps remain visible; one window never proves complete lifetime history.
3. Namespace flight identity by dataset/account/club and the validated source flight reference. The executable proposal uses an unambiguous tuple, independent of date, registration, crew and list position. Numeric IDs reflect the current probe candidate only; revise the adapter/contract if actual evidence differs.
4. An identical source record is unchanged. Repeated identical rows within a batch are counted once. Conflicting variants of the same ID require review; different source IDs are not merged merely because fields match.
5. Changed fields retain previous and next revisions. Manuel selected Vereinsflieger as authoritative on 18 October: latest verified provider facts supply the saved flight, including recorded duration rather than clock subtraction. Local/paper alternatives do not override them. Unknown/invalid/conflicting observations still require validation. Updating an existing saved flight creates an orange change indication under [#30](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/30); identical refreshes do not. Clear only by explicit acknowledgement, not opening/restart; acknowledgement does not correct source or paper. Incorrect provider records should be corrected in Vereinsflieger through club administrators/responsible personnel (Manuel, 18 October 2026). Preserve paper evidence and frozen writing snapshots separately; recheck scoped decisions against changed relevant evidence. These are selected product requirements, not implemented canonical behavior.
6. Omissions generate no deletion operation. Neither limited coverage nor a verified empty window proves source deletion. Deleted-flight handling requires independently established provider semantics and a review policy.
7. Apply an approved plan, source evidence and coverage atomically through the single SQLite writer. This persistence step, schema/backup changes, coverage scheduling and the real adapter remain to be implemented after verification and architecture review.
8. Report added/changed/unchanged/conflicting counts, last successful retrieval, verified periods and remaining gaps. Query imported history offline after force-stop/restart. A failed refresh is reported separately from usable saved history.

[Authenticated discovery](../verification/2026-10-10-vereinsflieger-discovery.md) explains the observed record-count/flight-total discrepancy: marked-row count matches the explicit duplicate count, and total records equal counted flights plus duplicates. Alternating backgrounds are independent striping in this sample. Preserve the explicit `Duplikat` field rather than rely on CSS or silently count every table row. No production duplicate policy or cross-configuration adapter is yet validated. Unknown crew/person IDs and roles remain unknown. Companion does not automatically mean instructor; a Pilot label does not establish PIC. The current canonical crew model cannot faithfully represent every raw provider distinction yet. ### Proposed identity and records

Use opaque local `ownerId`, `scopeId`, `flightId`, `bookId` and revision IDs. The owner is a persisted local identity, not the display name, `synthetic-pilot`, provider login or an assertion of cloud authentication. Each immutable provider scope belongs to that owner and carries provider-account/club references plus their evidence/verification state. Unique source identity is **(ownerId, scopeId, providerFlightReference)**; book IDs, registration, names, dates, row order and retrieval IDs never replace it. A changed/ambiguous account or club blocks association; a new local scope must not silently merge an old flight. Production activation requires the missing stable provider-scope evidence under #2/#16; a club label alone is insufficient. Future cloud linking is a separate explicit identity migration.

The following is a bounded proposed schema contract, not executed DDL. Every owned relation requires owner/scope consistency, including referenced IDs; foreign keys alone do not prove authorization. Actual versioned SQL/backup validation is reviewed before package B.

| Logical record | Required content and constraints |
| --- | --- |
| History manifest / source scopes | Schema/version, opaque owner, activation generation; immutable scope IDs, provider references and evidence state. One owner per isolated history file; registry authorization precedes opening it |
| Imported captures / bounded coverage | Capture ID, scope, original payload/checksum/version, adapter version, retrieval time, inclusive request bounds and successful page/count evidence. Same capture ID with different bytes rejects. Coverage proves only that bounded list; failed/partial attempts do not advance it |
| Source flights / fact revisions | Stable flight ID and unique scoped reference; append-only fact revisions linked to the immutable capture/row and mapping version; expected current revision for updates. Preserve raw field/crew slots, typed units, validation/conflict states, provider date, nullable UTC values and unresolved landing-day relation |
| Books / choice revisions | Separate owner/book/format-version identity. Per-flight explicit primary destination or deferral, eligibility evidence and source revision reviewed; at most one current primary credited membership. Reference-only links create no additional credit. A changed choice retains its predecessor |
| Import receipts | Unique commit/idempotency ID, owner/scope/capture, plan fingerprint, expected library generation and committed revision/choice counts. An exact repeated save returns its receipt; stale or different input cannot reuse it |
| Acknowledgement / paper references | Acknowledged source revision is distinct from current revision, book choice, assumed written progress and confirmed paper evidence. Exact acknowledgement edge cases and actual paper formats stay with #30/#7/#11; no paper progress moves on import |

An identical refresh records that the window was checked without manufacturing a changed flight or duplicate credited time. Repeated IDs with conflicting values stay unresolved; the user cannot invent a provider correction by choosing a local override. Later verified corrections append a revision and update current facts after the explicit save path. A mapping-version change alone is not a provider edit; distinguish re-interpretation from changed source facts. Omissions, including a verified empty window, never delete old flights.

The plan distinguishes **ready for history**, **history with deferred book choice**, and **pending source validation**. D1 allows supported incomplete fields in the first two states; it does not promote conflicting source variants, an invalid identifying date or an unverified scoped identity. Pending observations remain visible with reasons and retain any previous usable revision; they do not become counted current flights. Request coverage and the counts of saved, deferred and pending rows are separate facts. Invalid ownership/scope rejects the whole commit. Partial selection, if offered later, must be explicit and included in the plan fingerprint.

Incomplete saved facts under D1 would be visible in account history, including unassigned flights. Book eligibility and paper/export readiness are separate. Do not pass unknown crew through invented person IDs, derive a role from a name/slot, equate an unknown measure with zero or expose a raw clock as UTC. Later queries must report known totals and unknown counts separately; existing paper counters are not the fallback calculation. No real flight may be assigned to the current synthetic formats merely because a book is named gliding. If no approved real book/format is eligible, deferral remains available; actual edition-specific writing is a later gate.

### Proposed save and recovery contract

1. Resolve the exact authorized owner/scope and immutable capture. Validate complete bounded coverage and actual adapter evidence. Read a consistent library generation, relevant source revisions and eligible books; derive a deterministic plan without writes/provider calls.
2. Confirm only the displayed source revisions and book choices/deferrals. The plan fingerprint binds owner, scope, capture checksum, mapping version, base generation, target books and field/choice evidence. A stale plan returns for review without overwriting newer state.
3. Inside **one history SQLite transaction**, recheck owner/relations/generation, copy the already captured immutable payload once into imported evidence, append changed facts/choice revisions, update current pointers and bounded coverage, and write the idempotent receipt. No partially committed library state becomes selectable. The original capture database remains unchanged; no cross-database atomic commit is assumed.
4. Publish success only after commit and validated readback. A restart after commit but before acknowledgement resolves through the receipt; retry cannot duplicate flights, revisions or choices. A failed transaction leaves the prior history usable. Raw capture remains available independently throughout.
5. Opening/searching saved history works offline without provider login. Account/scope switching hides prior private rows immediately and preserves pending plans for their owner; pending confirmation cannot be transferred to another owner or book.

For D3, create a new candidate file through the existing local SQLite/selection architecture, with a new manifest and supported backup format. Validate every record/reference and reopen it before append-only activation. Retain the previous selection if creation, validation or activation fails; after interruption choose the newest fully readable committed generation. Do not overwrite an existing file or mix old schema-v1 dataset IDs with new source identities. Legacy raw data and journals remain where they are; only an explicitly selected, authorized capture can enter a future approved import. Backup/restore of the new format must include its imported evidence and independent book state, validate ownership/versions and preserve the old active store on failure. No live adoption or new backup writer occurs during this proposal.
