## Historical ID trust boundary

Use a persisted historical authenticated-profile ID receipt, whose provider is `vereinsflieger`; never substitute a local owner UUID, member number, club label, login-form text or arbitrary AI input. The [context validator/profile script](../../apps/platform-lab/src/vereinsflieger/context.ts) supplies the observed numeric account ID. AI04 adds a small `historical-provider-identity.ts` receipt adapter to the existing successful-profile/connection completion path: record the ID and provenance even if no flight was imported. Inventory the exact native completion hook in AI00. This is account-attribution metadata, not a provider credential or a server attestation.

For existing installations, a valid saved `snapshot.account.accountRef` plus the matching verified source binding can seed the receipt without another login; use the [saved-flight reader/service](../../apps/platform-lab/src/mobile/own-flight-reader.ts) and [source validator](../../apps/platform-lab/src/vereinsflieger/real-flight-source.ts) rather than trusting the ID's shape. A restored valid owner-scoped binding/receipt can preserve historical evidence; no current provider session is required. A prior successful login with an ID receipt but no flight binding must still admit general AI: keep the existing local-owner namespace, represent flight context as unavailable and never fall back to the synthetic book. Source-backed tools require the actual matching saved-flight binding. If no local owner exists, use the existing fresh-owner setup, without merging another owner's data. Ask for a first provider login only when no historical successful-profile evidence exists. Keep drafting/history available when identity cannot be established, and do not pretend a previous successful login was recorded if old versions never persisted its ID.

Every app-to-relay AI request includes the provider account ID. The relay validates shape, checks that AI is enabled for that configured account, and maps `(provider, account ID)` to a stable opaque billing tag. Only the opaque tag goes to OpenRouter usage metadata; the provider ID is not put in model prompts. Initially enable only Manuel's configured account. This allowlist does not prove who sent the request and does not authorize funding additional accounts.

**Selected tradeoff:** an ID observed by the genuine app is useful account evidence, but the number sent over HTTP is neither a secret nor a cryptographic assertion. A modified caller supplying a known enabled ID cannot be distinguished using the ID alone. Characterize that honestly in tests: reject malformed/unknown/disabled IDs, but do not claim a forged known ID is authenticated or rejected. Plausible consequences are misattributed spend, per-account quota exhaustion and consumption of the shared allowance. The initial server-wide EUR 1 cap, bounded calls, server rate/payload limits, no cloud flight/chat database and protected owner controls limit exposure; they do not turn the ID into verified server identity. Manuel's historical-ID rule selects this trust model, not legal compliance or automatic public/multi-user readiness. Revisit on observed abuse, broader enrollment/funding or future cloud/private-history access.

Keep private owner reports/configuration behind the existing backend operator access. Mobile requests return only their run status, minimal budget counters and current capabilities; no enumerable account/history/admin endpoint. Run-status/continuation handles must be unguessable and bound to the original account/run, not obtainable by enumerating IDs. Any minimal per-ID counter disclosure retains the same asserted-identity limitation. Do not add a hidden device-pairing or Supabase Auth requirement while implementing this plan.

## Protocol and storage contract to freeze in AI01

- **Context:** `{localOwnerId, provider, accountRef, contextVersion}` plus a discriminated available-flight context `{storeId, generation}` or `flights-unavailable`, and optional supported book selection. Book is not mandatory for current unassigned saved flights. A historical login alone can enable general questions without pretending missing flight data is an empty verified history. Pin a copied read snapshot/revision and release the lease. Before executing a tool or publishing an answer, recheck current selection/generation; a change interrupts the run and suppresses late output. Never read another account to finish the old run.
- **Request:** version, provider account ID, conversation/message/run/attempt/round IDs, supported client/tool schema version, requested feature, run capability, pinned policy ID and permitted user/tool/protocol input. The first call obtains its authoritative policy/run receipt from the server. Later calls cannot choose a model/prompt, change billing identity or replace earlier privileged protocol items. Server construction/validation owns system instructions; user/history/source strings never become privileged roles.
- **Reply:** `answer`, `needs-tools`, `needs-clarification`, `partial`, `unavailable`, `failed`, `cancelled` or `interrupted`, with validated tool declarations or plain-text answer blocks, opaque evidence/action/metric references, config/attempt receipt and settled/reserved/unknown budget projection. Render plain text and app-owned components; never execute model HTML/URLs/code. Validate references, schema, allowed actions and structured metrics; model-quality evaluation still checks unsupported narrative claims.
- **Tool operations:** `describeDataset`, `resolveEntities`, `queryFlights`, `aggregateFlights`, `getFlightEvidence`. Typed bounded filters and selected measures only; no SQL, generic filesystem/network/browser tool or provider writes. Pagination tokens bind account/store/generation/query and expire with the run. Return units, coverage, omitted/unknown counts and reference date/timezone for relative-period questions.
- **Crew query default:** look for candidate source labels only in the six declared slots, normalize Unicode/whitespace/case without silently merging spellings/people, deduplicate flights across matching slots, and expose the matched source slot. Ask for selection on ambiguous labels; describe latest/count among saved matching rows and qualify missing dates/coverage. This supports AI04 as a source-name query, not a confirmed-person/qualification assertion. Full person linking/credit remains deferred.
- **Projection:** task-local aliases for known people/registrations/source IDs, with local maps for display/navigation. Exclude complete raw rows/captures, remarks, credentials, Medical, invoices/member/training data, photos and unrelated settings. User text can still contain unknown personal identifiers; apply the existing disclosure. Clear alias/opaque reasoning maps when the active attempt ends; save only required user-visible evidence metadata with chats.
- **Chat storage:** owner-scoped conversation ID/title, monotonic activity sequence, context identity, messages/drafts, validated reply/evidence versions, attempt state/receipt and timestamps. Persist the input before dispatch. Empty New chat does not count until input persists. Max 50 per local owner, deterministic ID tie-break; eviction/deletion revokes local work but does not release uncertain server holds. All reads/writes/restore use owner/recovery gates. Backup v2 also includes the optional owner-scoped historical provider-ID/provenance receipt, even without flights; validate owner/account/source kind/version on restore, without treating the receipt as a secret or server attestation. Its presence never restores external-AI enablement or server quota.
- **Server storage:** account enablement/opaque tag, immutable config/prompt versions and active pointer, attempt/round/idempotency state, reservation/usage/conversion audit and minimal counters. No server flight/chat/remark/opaque-reasoning payload storage or payload logs. A non-content replay digest/run capability may bind continuity; it does not attest caller/provider identity. Persist dispatch intent before the provider request; exact duplicate rounds return the existing receipt/status, never another dispatch.
- **Failure:** no automatic billable retry/reconnect/resume. Timeout or ambiguous upstream outcome keeps a reservation and displays interrupted/unknown accounting. Reconcile later without reissuing inference. Keep partial output distinct from completed answers. New messages get the current policy; every dispatch additionally checks emergency disable, revoked permissions/routes, account enablement and remaining exposure.

### Detailed accounting and rollout boundaries

AI06 uses integer EUR micro-units and a recorded gross EUR-per-USD credit conversion covering applicable purchase fees/taxes. Calculate a safe maximum for the pinned route/context/output bound, with the reviewed uncertainty margin; if no finite safe bound exists, do not submit. A single database transaction creates/locks the account and app period counters, enforces both allowances and the active-attempt constraint, and records the reservation/dispatch intent. The model call occurs outside the database transaction. A late actual charge settles the original server admission period; never erase old unknown holds during month rollover or change periods using device time. Record differences and prevent further dispatch if an established bound/accounting invariant is violated. Test provider USD/UTC figures separately from the app EUR/Berlin counters.

The app's usage view shows settled, reserved/unknown, remaining, cap, calendar period and last reconciliation; update on admission/settlement, opening/foreground and the selected visible-only refresh interval. Owner totals/account/model reporting remains in the protected dashboard initially. OpenRouter analytics is a reconciliation source, not instantaneous authoritative EUR accounting. Remove only eligible settled metadata after the reviewed retention period; unresolved attempts remain until verified resolution. No scheduler/service needs adding merely to implement cleanup.

Every new account or widened overall allowance requires an explicit funding/access decision. Current ID-only admission does not authorize public enrollment or a larger aggregate cap. Future stronger proof, device attestation or cloud accounts are follow-up options, not prerequisites silently inserted into this implementation.
