# MoFlight project plan

Updated: 2026-10-13 (Europe/Berlin). Product/decision owner: Manuel Singer. This roadmap was explicitly authorized by Manuel on this date. It is the authoritative source for current priorities, milestone status and next actions; it does not claim acceptance of unfinished features or proposed architecture.

## 1. Direction and constraints

**Current focus: basic UI and application contract → reliable retrieval → saved live history → initial analytics. Writing-template expansion and other feature implementation follow later.**

- Keep phone-local SQLite and offline access as the initial persistence path. Retain the approved Expo/React Native/strict TypeScript stack and one native database writer.
- Establish a clear boundary: **screens → application operations → domain/repositories → provider/platform adapters**. Screens consume typed results and status; SQL, provider markup and recovery sequencing belong below the UI boundary.
- Extract browser orchestration from the access screen in a bounded refactor. Preserve working domain/persistence modules; add modules only when required. No rewrite, microservices or generic plugin framework.
- Retain browser retrieval and plan a second REST path conditionally on permission and feasibility. Both adapters must feed one downstream evidence/normalization contract; the UI must not depend on provider transport details.
- Preserve raw evidence, unknown fields, units, identity and coverage. Deterministic code owns counts, durations and statistics; optional AI cannot silently establish facts or perform arithmetic.
- Default planning assumptions: one app, manual retrieval, local storage and deterministic analytics. One app is a working assumption, not a final release-packaging decision. Source-flight/account identity stays separate from book identity, format and paper progress.
- Defer implementation of writing expansion, AI/chat, cloud integration, tutor and weather. Preserve cloud/SPL/handwriting feasibility obligations and platform/privacy gates; deferment is not removal from requirements. Supabase Cloud Free remains the selected first cloud trial, not a prerequisite for local analytics.

Documentation responsibilities: this plan controls order and completion criteria; [README](../README.md) remains the central project entry point; [product specifications](product/README.md) and ADRs hold detailed requirements/decisions; GitHub Issues hold tasks/blockers; dated verification reports hold evidence. [The requirement register](verification/2026-10-11-project-audit-register.md) retains R01–R15 and FL-01–FL-17 identifiers; its dated statuses are historical, not the current roadmap.

This authorized sequence supersedes conflicting writing-first, chat-next and early parallel feature-execution instructions in older planning documents, including the scheduling portions of ADR 0004/0008. Accepted local-first, evidence/AI, ownership and validation boundaries remain applicable. [ADR 0007](adr/0007-multiple-logbooks-and-formats.md) remains proposed; bounded synthetic implementation does not approve the production schema. [ADR 0008](adr/0008-logbook-ai-and-deterministic-boundary.md) still requires an approved, bounded handwriting evaluation before completing the real photo-to-writing journey. [ADR 0009](adr/0009-local-android-development-and-checkpoint-ci.md) requires relevant documented local checks/builds/native trials; hosted CI remains optional/manual-only, with no paid CI or AI authorized here.

### 1.1 Agreed development workflow — 2026-10-13

Manuel confirmed this way of proceeding on 2026-10-13: design the user journey and application interface together, then develop UI and underlying logic in small, testable steps. This records the working method and design-tool direction; it does not approve unfinished screen designs, analytics definitions, production architecture or automatic implementation of M1–M5.

| Part | Responsibility | Example |
| --- | --- | --- |
| UI | Present information, accept actions and display operation states | Flight list, filters, retrieval button and progress |
| Application logic | Perform operations and enforce retrieval, persistence, recovery and calculation rules | Retrieve flights, preserve history after failure, calculate deterministic totals |
| Interface contract | Agree requests, results, scope and observable behavior between UI and application logic | Saved-flight query parameters/results; retrieval progress, cancellation and recovery states |

The interface contract is an internal software agreement, not a requirement for a web API or server. UI and logic can develop separately behind that agreement: synthetic and real implementations must satisfy the same contract. Visual changes usually stay within the UI; new measures or changed behavior may require coordinated contract and logic changes. Existing lab separation is partial; M1 specifies the boundary and M2 extracts retrieval orchestration.

For each bounded feature:

1. Describe a real user journey and the information/actions it needs.
2. Sketch screens and navigation with simple boxes and labels before visual polish.
3. Define behavior and the operation/state matrix alongside the sketches: loading, empty results, cancellation, expired connection, failed refresh, offline/stale history, incomplete coverage and pending recovery. Specify inputs/results, account/book scope, evidence and unknown values.
4. Review a clickable prototype with Manuel before scoped application implementation. Manuel judges usefulness, wording, navigation and ease of use; the engineer handles contracts and technical feasibility.
5. Implement reusable React Native UI elements against clearly labeled synthetic results using the reviewed contract. Sample results demonstrate behavior, not live-provider or production acceptance.
6. Connect real application operations one journey at a time as the relevant milestone dependencies are satisfied, then verify complete phone journeys including failure and offline states. Repeat and refine; do not require every future feature to be designed before starting a reviewed slice.

**Tool direction:** use Figma Design as the main workspace for reviewed layouts, reusable components, states and clickable prototypes. Google Stitch is optional for quickly exploring visual directions; refine the chosen direction against MoFlight requirements. Translate reviewed designs into the existing Expo/React Native application and connect them through the contract. Generated screens/code require adaptation and verification; they do not establish native behavior or replace phone testing. Advanced design-to-code integrations can follow when useful. This choice does not authorize subscriptions, paid usage or a change of application stack.

Capability references checked 2026-10-13: [Figma prototypes](https://help.figma.com/hc/en-us/articles/360040318013-Play-your-prototypes), [Figma Code Connect](https://developers.figma.com/docs/code-connect/) (including React Native support), [Google Stitch overview](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-updates/). These inform the tool direction, not an acceptance claim or a promise of automatic native code generation.

**First M1 review slice:** overview → filtered flight list → flight detail, with retrieval progress and failure examples. Use this representative journey to settle navigation and visual direction, retaining connection/retrieval and settings in the overall M1 wireframe scope. Counts, known durations, date/aircraft breakdowns and person/role/latest-flight queries remain proposals for review; costs remain gated on their definition. M1 remains next, not completed. REST permission informs M2 and need not delay M1 preparation; deferred writing, chat, cloud and other features retain their existing gates.

### 1.2 User journeys and UI concept discovery — 2026-10-13

Manuel confirmed that user journeys and the overall UI/design concept are the next discovery step, to explore which features matter to users and what is feasible before fixing detailed interfaces. The engineer leads the discussion in plain language and records confirmed needs separately from assumptions.

Start with user situations, desired outcomes and current difficulties; identify essential features, useful additions and later ideas. Assess each candidate against existing evidence: supported by current capabilities, dependent on retrieval/history work, or dependent on new permissions/technology. Explore two or three rough UI approaches with realistic examples and review the journeys through them. Future features can appear as clearly labeled concepts without being scheduled for implementation.

The first deliverable is a small set of user journeys, a feature-priority/feasibility map and rough screen concepts. Then refine selected journeys into detailed behavior and application contracts. This refines M1 preparation rather than changing M2–M5 order or their gates. The earlier overview → filtered flights → flight detail slice is a starting hypothesis, not a frozen navigation decision. [Discovery brief and guided questions](product/user-journey-ui-discovery.md) track the work; initial ideas are not validated user research.

**Immediate task:** lead [user-journey and UI concept discovery](product/user-journey-ui-discovery.md): establish users, useful situations and desired outcomes; produce a small journey set, feature-priority/feasibility map and two or three rough UI approaches for review. Then prepare M1 wireframes and an operation/state matrix for the selected journeys. This roadmap specifies that deliverable; it does not yet freeze interface signatures or implement controllers.

**Acceptance scenarios for subsequent work:** successful/empty/paged retrieval, cancellation and failed refresh preserving prior history; interrupted cleanup and same-account recovery; rejected foreign scope; identical/changed/duplicate imports and partial coverage; ambiguous persons, unknown roles/units and missing values; backup restore and offline restart; exact contributing-flight lists and totals. Choose work from this sequence; identify a priority change explicitly instead of starting an unrelated service. Update this plan when priorities, status or material decisions change. Keep detailed commands/results in dated verification reports. Check current Issue state before changing tasks or creating duplicates; do not close an Issue merely because a bounded proof passed. Discovery/readiness tracking may continue without scheduling deferred feature implementation. No deadlines are promised beyond the expected decision follow-up below.
