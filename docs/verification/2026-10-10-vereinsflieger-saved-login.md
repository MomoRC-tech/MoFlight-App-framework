## Authorization and implementation

Manuel explicitly authorized saving and using his login on the emulator for the development phase, explaining that repeated desktop sign-in handoffs prevent remote work from his phone. Optional app-owned password saving is approved for this scope. The password is not present in source, fixtures, documentation or commit messages.

- Separate opt-in MoFlight credential-entry screen with masked password and Save/Cancel; values are cleared from React form state after successful save/cancel. The user supplies credentials once; prior provider sign-in did not collect them.
- Pinned `expo-secure-store` 57.0.4 matches the installed Expo 57 `bundledNativeModules.json`; no framework upgrade. Native storage uses a separate service/key, device-only unlocked accessibility on iOS and no per-use biometric prompt. This supports remote development while the device/app is available.
- A nonsecret installation marker in the app sandbox prevents automatically reusing iOS Keychain credentials that survive an uninstall. SecureStore availability is checked; storage failures are reported generically without supplied values.
- Android `allowBackup=false` remains configured and the SecureStore plugin adds exclusions for legacy backup, cloud backup and device transfer. Logbook JSON backups only contain the logbook records and do not access SecureStore. Browser-cookie backup/logout is a separate open check.
- Use saved login is an explicit one-attempt foreground action. It opens the exact observed `https://vereinsflieger.de/` login page, writes app-supplied credentials into the original uniquely identified form and clicks its original submit control. It does not read existing page credential values, hidden salts, cookies or password managers, and does not add a data-extraction bridge to login pages. Changed/ambiguous forms, frames, unrelated pages and external actions receive no credentials.
- No success is inferred merely from a navigation. The provider response remains visible for account/verification checks; retrieval is a separate action. A 30-second timeout ends the attempt without a retry loop. Challenges/2FA/rejection can still need direct provider interaction.
- Forget saved login removes the protected username/password; existing browser cookies and captures are preserved. It is not provider logout. Disconnect/account-switch lifecycle remains open.

Technical references: [Expo SecureStore documentation](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/) and [official source](https://github.com/expo/expo/blob/main/docs/pages/versions/unversioned/sdk/securestore.mdx), plus the installed pinned package's API/plugin source. The SDK 57 documentation URL was inaccessible through web lookup; pinned compatibility was verified locally rather than inferred from the latest docs.

## Actual Android build/install and session continuation

Local standalone Android Release build from `6bcf5b93e467c77f308cc3fe4c6ba82ea3448b20` succeeded in 6m55s, with 585 tasks executed after native regeneration. Binary size: 46,879,559 bytes. SHA-256: `4e97b73c2f5066b02fab1ea65ee3dacc416a8dc74f8db2ba283e0454a3937021`. Embedded JavaScript and arm64-v8a/x86_64 libraries checked. Android/iOS Hermes exports also passed; iOS native execution remains untested.

Generated and merged Android manifests were inspected: `allowBackup=false`, SecureStore `fullBackupContent`/`dataExtractionRules` references present. The installed pinned module's XML excludes SecureStore preferences from legacy/cloud/device-transfer backups. No biometric/Face ID permission prompt was added. Both native and JS SecureStore modules are part of this build.

Installed with `adb install -r`, without uninstall or app-data clearing. First immediate launch after update crashed with a React Native/Expo activity-lifecycle assertion: “Pausing an activity that is not the current activity.” Cause is not established. A clean force-stop/cold launch succeeded, and a second independent cold launch also succeeded. This recovery is not a code fix or evidence that the transient lifecycle issue cannot recur; it is tracked in #6.

The updated access screen opened with the original stored capture timestamp/fields unchanged and without a protected-storage initialization error. Showing the provider page displayed the signed-in dashboard and the provider's own confirmation that stay-signed-in was marked, independently corroborating the user report. An explicit retrieval reused that session, saved 20 raw rows with a new timestamp and required no credential re-entry. After the second force-stop/cold launch, the new capture reopened unchanged. Original captures and synthetic dataset state remain preserved. No stored app password was needed for these checks; session cookies are the primary mechanism.

The empty, masked app save-login form was visually checked and left ready for the user's one-time entry. The user subsequently reported completing Save login. The access screen showed Replace/Use/Forget saved login. A further force-stop and cold launch succeeded (714 ms); reopening the access screen showed the same saved-login controls after the protected-storage read, without a storage error. This verifies recognition of the saved protected entry across a process restart without inspecting or logging its values. The existing capture also reopened unchanged.

Actual provider authentication using the saved fallback and Forget remain untested. The working stay-signed-in session was not cleared merely to force a login challenge, and the saved credential was not removed merely to test deletion. Export bytes, complete history and canonical import remain separate open work under #2. No personal values/screenshots/runtime databases are included in Git, and no native smoke clearing app data was run.
