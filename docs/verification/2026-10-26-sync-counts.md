## Implemented behavior

- Flight retrieval shows validated received rows against the provider-reported total, advancing by whole pages. Before the first validated page the total is unknown (`0/?`); a validated empty list is `0/0`. No per-row streaming or estimated percentage is claimed.
- Flight saving shows `0/N` until atomic save and stored-library readback succeed; the completed row retains `N/N`. N counts incoming flight rows, including already known flights, rather than newly added records or the whole local library.
- Medical, events, document notices, annual work summary, work entries and tasks use `0/1 Anfrage`; duties use two actual page requests (`0/2`, `1/2`, `2/2 Anfragen`). These are requests, not a claim about complete source histories. Preparation, account proof and sign-in use a single step. Waiting for sign-in has no invented time estimate.
- Both visible and accessibility text include counts. A new stage resets its active count, the last confirmed stage retains its count, and failed/backgrounded/cancelled or late-stage updates cannot promote another stage. Existing source freshness, owner/store scoping and partial-source semantics remain in place.

### Recommended approach

1. **Measure nonoverlapping work units.** Preparation, account verification, provider setup, page retrieval, source review, durable save, receipt/readback and optional sources need attempt-scoped starts/ends. Keep the existing two text rows, but expose the actual substep when flight retrieval has finished and checking begins. Scope callbacks and samples to owner/store/run/stage; obsolete attempts cannot advance or train another run. Address #90's correlation gaps first.
2. **Learn locally from comparable successful foreground runs.** The first success supplies a provisional sample; a rolling median of the last five suitable samples is a simple starting proposal. Separate fresh/repeat/resume work, device, timing-model version and broadly comparable volume. Separate local-storage from network timings. Existing library size, incoming rows/pages and changed records may affect cost. Start with simple buckets; only fit fixed-plus-per-page/row costs when enough observations support them. Do not multiply the first flight's time by the number of flights: navigation/profile/validation impose fixed overhead. No network reporting is needed.
3. **Weight by expected duration.** Freeze estimates for the scheduled work at attempt start. Overall estimate = (expected duration of confirmed completed units + estimated portion of current unit) / expected duration of all planned units. Medical and flight saving should not have equal weights. Resume plans only remaining work and is labelled as continuation.
4. **Use real evidence where available.** Validated rows/pages drive the retrieval portion; setup, review and save/readback retain separate budgets. Exact text counts remain exact. For opaque work, a proposed initial fraction is `min(0.9, 0.9 * foregroundElapsed / expectedDuration)` until actual completion. The 90% cap is a tuning proposal, not a measured optimum. Early confirmed completion advances immediately to the unit's end. Show approximate overall progress, without precise remaining seconds while evidence is sparse.
5. **Make uncertainty visible.** With no useful estimate, use indeterminate activity and learn from the first completed run. Label the estimate, for example `Gesamtfortschritt ca. 65 %`, separately from `Flüge abrufen (4/101)`. At the cap, stop advancing and explain that the step is taking longer, retaining activity feedback instead of creeping endlessly toward 99%. Freeze during login/background waits. Failure/cancellation stops the run; finished-with-errors stays partial, never green 100% success. Revise the next run's model rather than making the current bar move backwards. Only confirmed completion reaches 100%.

### Ordered implementation plan

1. **P1 - trustworthy stage events and baseline (#90/#41).** Add an attempt-scoped event contract for start, count, finish, wait/resume and terminal outcome, with unique parent/child span identity and monotonic foreground duration. Drive diagnostics and progress from the same coordinator events. Record nonoverlapping top-level stages plus labelled nested details; distinguish queue wait, DB opening, graph read, replay, derivation, writes and readback. Capture only bounded counts/durations, with no source payload. Acceptance: synthetic nested-span, cancellation/late-callback and account-switch tests; a complete timeline whose top-level durations and explicit gaps reconcile with the operation wall time. Keep background/user waiting separate. Establish fixed-input baselines before optimization.
2. **P2 - smallest local optimization PoC (#41).** Start with post-commit exact-byte validation reuse and duplicate snapshot elimination, then evaluate operation-scoped repository/readback reuse if profiling justifies it. Journal changes are a subsequent bounded commit only if scans remain material. Keep current schema, FULL durability, source evidence, receipt semantics and authorization. Acceptance: equal complete graph/receipt results, mutated same-generation data rejected, foreign lease/selection rejected, uncertain commit/crash recovery, rollback and offline reopening. A failed/rolled-back transaction must never publish cached validation. Test no-change and changed imports with different accumulated receipt histories; a later identical import can still append evidence and advance retrieval freshness.
3. **P3 - deterministic estimator and local learning (#92).** Implement a pure reducer consuming P1 events, an injectable clock and duration samples. Store a small bounded set of successful stage samples in existing owner-scoped local persistence; treat them as disposable performance hints, outside user backup/business data. Use timing-model version, scope, first/repeat/resume and volume buckets. Freeze weights per attempt; use validated counts only within the relevant substep, capped elapsed-time fractions elsewhere. Pause or become indeterminate for unknown work. Reject obsolete callbacks; support continuation as remaining work. Reset incompatible samples after performance/model changes so old slow timings do not distort the optimized build. Acceptance: deterministic fake-clock tests for cold start, empty source, paging, outliers, early/late completion, pauses, retry/resume, failures and monotonicity.
4. **P4 - existing indicator integration (#92).** Feed the estimator to the current Sync ring and retain the two status rows, exact counts and honest substep labels. Use indeterminate activity until an estimate is useful, label estimated progress, and reserve success for confirmed completion. Isolate low-frequency estimate updates to the progress component so animation does not rerender the whole library. Preserve reduced motion, cancellation guards and partial/error states. This follows the referenced Material determinate/indeterminate components with MoFlight's existing Compact Cockpit styling; changing to a horizontal bar would be a separate selected appearance choice.
5. **P5 - one integrated checkpoint (#90/#41/#92).** After focused host tests during editing, run one full host check and one committed-source Release/native checkpoint for the stable package. Compare baseline/candidate on the same device and cloned initial data, separate cold launch, repeat sync, changed/no-change imports and resumed work. Restore the same baseline between timed trials: otherwise accumulating receipts can confound results. Aim for five comparable observations per selected scenario, reporting samples/median/range and harness overhead. Replay the estimator with earlier-run samples only and measure prediction error and time spent capped. Require real repeatable wall-time improvement for a speed claim and unchanged correctness. Inspect only the affected indicator/state; Android, physical-phone, live-provider and iOS claims remain separate.
