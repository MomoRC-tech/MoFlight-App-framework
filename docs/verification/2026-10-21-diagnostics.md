# Support diagnostics — 21 October 2026

Tracking: [#46](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/46). Manuel requested implementation of an anonymized recent-operation journal, a separate Settings screen and user-controlled export. M1 support/settings with M2/M3 reliability dependencies; #41 performance investigation remains separate.

## Implemented contract

Settings → **Diagnose öffnen** opens a separate, scrollable screen with contextual Back, newest-first operation cards, **Diagnosebericht teilen**, selectable JSON for copying, and **Diagnosejournal leeren**. Existing shared dark cards/actions and a centered 520 dp content cap are reused. No dependency, remote telemetry or automatic message delivery was added. Native text sharing opens the OS chooser; the user chooses the recipient/application and sends. Long-press/select/copy is the clipboard fallback, rather than a dedicated copy button.

The installation-local journal retains at most five operations across process restarts in `moflight-support-diagnostics-v1.json`, outside account/book databases and their backup formats. It tracks own-flight loading/update, opening flight tools, library operations, local list/detail reads, results, total elapsed milliseconds, fixed failure/gate codes and aggregated phase calls/failures/timings. The combined update includes owner setup, source retrieval/review, save/receipts and optional Medical; Medical failure is a partial outcome after a successful flight save. Background/cancellation, account mismatch, pending recovery, source timeout, provider handoff and interrupted restart remain distinct. This is a bounded operational journal, not a record of every navigation tap or a general crash logger. Existing provider/development console logs are not imported into it.

Privacy is enforced by construction: action/stage/outcome/code allowlists and bounded numeric durations/counters only. No names, account/book/flight identifiers, dates/windows, routes, registrations, Medical contents, URLs, credentials, arbitrary errors, stack traces, wall-clock timestamps or device identifiers enter this report. Stored input is reconstructed through the same allowlist. Operations from previous users of the same installation contain no owner references. No identity hash or cross-user correlation ID is generated. The local sequence is only an ordering counter. Timing and operational patterns remain technical metadata; this is not a blanket legal anonymization assessment.

Completed stages retain their original operation even when another action starts. Clear/eviction prevents late completion from resurrecting records. Restart marks unfinished operations **interrupted**, without claiming a failure cause. Nested phase times overlap and must not be summed. Writes are small and best effort; phase writes are coalesced at 250 ms, while start/end/clear persist immediately. Persistence failures preserve the in-memory report and show a warning. A crash or failed write can lose the last update; no transactional crash-durability claim. Clearing affects this journal only; copies already sent/shared remain outside the app.
