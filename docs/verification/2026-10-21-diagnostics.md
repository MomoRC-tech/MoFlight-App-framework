## Implemented contract

Settings → **Diagnose öffnen** opens a separate, scrollable screen with contextual Back, newest-first operation cards, **Diagnosebericht teilen**, selectable JSON for copying, and **Diagnosejournal leeren**. Existing shared dark cards/actions and a centered 520 dp content cap are reused. No dependency, remote telemetry or automatic message delivery was added. Native text sharing opens the OS chooser; the user chooses the recipient/application and sends. Long-press/select/copy is the clipboard fallback, rather than a dedicated copy button.

The installation-local journal retains at most five operations across process restarts in `moflight-support-diagnostics-v1.json`, outside account/book databases and their backup formats. It tracks own-flight loading/update, opening flight tools, library operations, local list/detail reads, results, total elapsed milliseconds, fixed failure/gate codes and aggregated phase calls/failures/timings. The combined update includes owner setup, source retrieval/review, save/receipts and optional Medical; Medical failure is a partial outcome after a successful flight save. Background/cancellation, account mismatch, pending recovery, source timeout, provider handoff and interrupted restart remain distinct. This is a bounded operational journal, not a record of every navigation tap or a general crash logger. Existing provider/development console logs are not imported into it.

Privacy is enforced by construction: action/stage/outcome/code allowlists and bounded numeric durations/counters only. No names, account/book/flight identifiers, dates/windows, routes, registrations, Medical contents, URLs, credentials, arbitrary errors, stack traces, wall-clock timestamps or device identifiers enter this report. Stored input is reconstructed through the same allowlist. Operations from previous users of the same installation contain no owner references. No identity hash or cross-user correlation ID is generated. The local sequence is only an ordering counter. Timing and operational patterns remain technical metadata; this is not a blanket legal anonymization assessment.

Completed stages retain their original operation even when another action starts. Clear/eviction prevents late completion from resurrecting records. Restart marks unfinished operations **interrupted**, without claiming a failure cause. Nested phase times overlap and must not be summed. Writes are small and best effort; phase writes are coalesced at 250 ms, while start/end/clear persist immediately. Persistence failures preserve the in-memory report and show a warning. A crash or failed write can lose the last update; no transactional crash-durability claim. Clearing affects this journal only; copies already sent/shared remain outside the app.

## Diagnostic usefulness review and proposal — 21 October 2026

Manuel requested reasoning about useful support information, timing coverage and Android facilities. [#47](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/47) records the proposed follow-up contract. **Proposal only: no additional implementation, native integration, SDK/service adoption, spending or priority change is approved.** #46 remains complete for its original scope; #41 owns the separate latency investigation.

Source inspection confirms that total elapsed time and completed phase timings are already exported. Owner setup, source retrieval/review, provider view/export steps, commit/receipts, Medical and local reads have named instrumentation. **Login and protected-profile verification have no dedicated timers.** The broad source-retrieval interval can include user sign-in/account-confirmation waiting, provider navigation/export and view restoration. Its duration is not provider-server latency. Nested phases overlap; repeated phases currently expose summed duration/call/failure counts, without their ordering, maximum individual duration or an active-phase checkpoint. Existing SQL/hash/transaction/open/owner-guard counters are console diagnostics, not part of the support export.

The highest-value proposed package is to add build/Android/WebView context; group five meaningful user journeys with their internal reads; protect one bounded last-failure record from routine-read eviction; split observable login/user-wait/profile/source/save/readback phases; and record ordered checkpoints, active phase, retry/timeout, fixed error layer/gate and verified save/recovery state. Use explicit operation attribution for counters/spans. Optional flight-row/page size buckets should be justified separately; technical metadata is not automatically legally anonymous. No personal/source/Medical values, credentials, arbitrary URLs/errors/stack traces or stable user/device identifiers. Exact scope, proposed seven-day last-failure expiry, tests and approval boundary are in #47 rather than duplicated here. Measure diagnostic overhead: synchronous file writes are present, but have not been established as a performance bottleneck.

Official Android documentation was checked on 21 October 2026:

- [ApplicationExitInfo](https://developer.android.com/reference/android/app/ApplicationExitInfo) and [ActivityManager exit history/state summary](https://developer.android.com/reference/android/app/ActivityManager) provide Android 11/API30+ process-exit information. A separately selected small native adapter could report categorical exit reasons with supported-version fallback and correct process/operation correlation. History is limited; unavailable information stays unknown. Raw system descriptions and ANR traces would remain excluded. These APIs do not explain handled provider failures or measure login.
- [Logcat](https://developer.android.com/studio/debug/logcat) helps developer-side investigation, including native exceptions. [Android logging guidance](https://developer.android.com/privacy-and-security/risks/log-info-disclosure) supports predictable, non-sensitive messages and limiting production logging. The custom support report should remain allowlisted; full device logs are unsuitable as its default export.
- [Trace/Perfetto custom events](https://developer.android.com/topic/performance/tracing/custom-events) can connect named phases with system performance traces for targeted #41 work. [StrictMode](https://developer.android.com/reference/android/os/StrictMode) can expose accidental main-thread I/O in development, with best-effort limitations. Neither replaces the business-operation journal.
- [Android vitals](https://developer.android.com/google/play/vitals) supplies Play-distributed app-quality monitoring, subject to user data sharing; it is a later release tool rather than the current sideloaded support report. [ProfilingManager](https://developer.android.com/reference/android/os/ProfilingManager), added in API35, supports on-device profiling, but is deferred in this proposal as unnecessary complexity/overhead for the small default report. No third-party telemetry SDK or backend is currently recommended.

Verification for this review is source/reference/claim consistency only. No application source was changed; no app tests, builds, emulator actions, provider access or model/service execution were performed for the proposal.

### Superseding history direction and observed journeys

Manuel subsequently rejected five entries as much too small and suggested using a longer record to recover actual user paths, discover unexpected journeys/possible intentions and improve the product. This supersedes the five-journey retention recommendation above. [#47's updated proposal](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/47) owns the candidate budgets and acceptance details: an initial evaluation target of 2,000 meaningful user actions/navigation transitions, separately bounded technical events, 14 days and 5 MB overall (first limit reached). These are proposed limits to validate, not measured capacity or implemented values. Reserve capacity for failure context and keep routine technical reads from evicting the action trail.

Proposed action vocabulary includes screen/dialog entry, named action/result, Back/Close, retry/cancel, filter kind changed/reset, lifecycle and relative timing. Exclude entered values, flight/owner/book identities, touch coordinates, replay media and provider-page content. Reconstruct observed paths without requiring predefined funnels; use alternate routes, repeated actions, backtracking and waits to generate journey hypotheses. Navigation does not establish intent, confusion or abandonment; validate those interpretations through user feedback. Submitted support reports are a self-selected sample and cannot establish representative usage rates.

Keep failure diagnosis and product-learning views distinct over a shared bounded event foundation. The default remains local storage and explicit user-controlled report sharing. No automatic behavioral upload, cross-user tracking, new vendor/backend, session replay or LLM processing of submitted reports is authorized. First proposal: capture a longer trustworthy history; separately evaluate journey summaries/analysis afterward. No application implementation or priority change follows from recording this refinement. Documentation/Issue consistency was checked; no application tests or devices were needed.
