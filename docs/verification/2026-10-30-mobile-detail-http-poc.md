## Implemented boundary

Open **Profil → Entwicklung → HTTP-Flugdetail vergleichen**. Opening this tool first asks the existing provider controller to release its idle browser, then unmounts that controller. Active Sync, account changes, storage, information requests and activity checks prevent release. The main Shell and its drafts remain mounted. Closing remounts the ordinary controller against its existing persisted store; cookies, saved credentials, flight library and books are not cleared.

The explicit live action loads the protected profile, checks any already confirmed provider account, and requires confirmation of the observed account/club. Same-origin WebView `fetch` then reads a fresh profile, the visible own-flight list, its first valid observed detail reference, and a final profile. All requests are GET with same-origin credentials, no-store and rejected redirects. Cookies stay inside the WebView. Exact URL/content-type, byte/charset bounds, login forms, list structure, account/club and a 10-second script deadline guard the operation. The existing allowlisted detail reader parses an inert document; billing sections remain excluded. No caller-supplied ID, guessed ID, Node API, API Anything runtime, cookie bridge or native HTTP library is introduced.

Normal detail navigation reads the same reference with the original reader, then a fresh protected profile must confirm the account again before comparison completes. Exact and whitespace-normalized comparisons are distinct; original observations are retained. Native nonce/origin/document guards, foreground ownership, per-navigation epochs, cancellation and watchdog renderer revocation reject stale work. Failures preserve accepted earlier observations and saved library data. Persistence failures are displayed explicitly.

Append-only raw trial evidence is isolated in the app-private SQLite file `vereinsflieger-detail-http-poc-<SHA256-local-owner>.sqlite`, scoped by the local owner and separate from the library and book schemas. It can contain the observed account/club and allowlisted flight fields; it is not exported to logs/GitHub. Synthetic results and fixed live stage/error categories, booleans, timings and field-comparison counters are logged for local verification. The sanitized live projection excludes identity, source IDs, URLs and raw values; a regression verifies that exclusion. No secret or personal fixture is committed.

### Why preparation and login appear slow — source inspection, 30 October

The same owner Sync reaches its flight stage at 22,266 ms. About 7.8 seconds precede the first retained `sync-prepare` checkpoint (owner setup alone 7,695 ms), explicit preparation takes 2,470 ms, and the account-labelled stage takes 11,958 ms. That label is broader than provider authentication: `loadFlights` sets “Anmeldung wird geprüft” before `retrieveUpdateWithStoredReadback` calls `plannedUpdateRequest`, which performs pending-command recovery and opens/reads the selected flight repository before asking the controller to verify the provider session. Across the operation, four recorded native `session-verification` spans total 2,596 ms; that does not include the additional profiles inside the guarded HTTP page request. The whole account-stage delay must not be described as login-network latency.

Source and recorded counts identify expensive repeated local verification:

- [`RealFlightLibrary.open`](../../apps/platform-lab/src/vereinsflieger/real-flight-library.ts) always reads and validates the graph. [`validateRealFlightGraph`](../../apps/platform-lab/src/vereinsflieger/real-flight-library-model.ts) replays all saved command receipts, rederives expected records and verifies their semantics/hashes, rather than just checking that the file opens. The report has four graph validations totalling 20,115 ms and two repository opens totalling 12,688 ms; these overlap, not separate costs to add.
- [`RealFlightService`](../../apps/platform-lab/src/vereinsflieger/real-flight-service.ts) opens separate sessions for initial planning and post-retrieval review/save. Initial owner admission also validates the selected candidate, and writes retain fresh post-write validation. Exact-content reuse already exists within one library handle, but closing that handle discards its cached validation.
- [`RealFlightCommandJournal`](../../apps/platform-lab/src/vereinsflieger/real-flight-command-journal.ts) similarly caches validated command rows only per handle; reopening validates historical commands/source evidence again. Entry refresh calls `prepareFreshFetch`, update planning calls it again, then `retrieveSource` checks pending commands again. Some boundary checks are intentional; six journal opens total 11,091 ms in this run. Actual native database-open counters within these spans total only 29 ms, so “opening” here mainly means the surrounding admission/validation path, not simply creating a SQLite connection.
- [`InformationRun`](../../apps/platform-lab/src/vereinsflieger/information-run.ts) fences each additional source with profile/read/profile navigation, and the ordinary jobs run sequentially through the shared browser. The seven other-source stages total 15,300 ms in this observation. No evidence establishes that all of those guards can safely be combined or removed.

These are runtime account, integrity and recovery checks, not the development test suite. Ordinary Sync does not call the explicit Development synthetic proof. Pause hooks initialize off; watchdog timeouts limit stalled operations rather than deliberately waiting out their full duration. Diagnostic counters/logging do run and periodic persistence is scheduled; their independent overhead has not been measured, so this inspection does not claim zero overhead or blame them for a quantified part of the delay.
