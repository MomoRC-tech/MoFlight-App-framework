Issue [#91](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/91); P2 / M2–M4; R04/R12, FL-03/10/11 and E07/E09/E11. Manuel selected recovery after the app returns or restarts. This package does not run provider work while backgrounded.

## Implemented contract

Application source `c3b7275dde3b562e22a2a52db0400d2a9d682b19` persists an owner/store-scoped Sync marker and successful optional-source statuses in a separate local SQLite file. Flight evidence and import receipts remain in the existing flight library. An interrupted Sync offers **Fortsetzen** or **Neu synchronisieren** when opened again. Continuation first reconciles the saved flight capture and committed receipt, then verifies the same provider account and club. A matching saved flight is not imported again; completed optional sources are skipped and unfinished sources are retried. A changed or unverified account cannot continue. Existing local data and explicit cancellation remain protected.

The progress marker contains only owner/store IDs, provider account reference and club label, capture ID, timestamp and source statuses. It contains no credentials, raw provider page, flight rows or Medical content. It is local to this installation and is not a new cloud or manual-backup format.

## Interrupted-attempt correction — 26 October 2026

[#93](https://github.com/MomoRC-tech/MoFlight-App-framework/issues/93), follow-up to #91/#90/#41; R04/R12, FL-03/10/11 and E07/E09/E11. Manuel supplied a private support report from `18eae2e` after reporting that Sync did not work. He subsequently confirmed that Sync completed when MoFlight remained visible throughout. This is user-observed foreground success, not an independently executed live-provider acceptance run.

The report contains two update attempts diagnosed as cancelled/background. Subsequent foreground returns nevertheless produced new account/retrieval/review/save events, followed by failures. A final attempt was still running when the report was exported; it is not evidence of an additional completed failure. The first recovery dialog appeared approximately 46.7 seconds after Sync request and the second after 41.7 seconds. Expensive repeated local validation and recovery reads are visible. These interrupted attempts do not provide a comparable before/after complete-Sync speed measurement. Private input remains in ignored attachment storage.

Source inspection and deterministic regressions reproduced a defect: the coordinator's active check depended on current foreground state, so returning could make an already-cancelled attempt active again. Continue also lacked interruption checks between asynchronous local reads and new provider admission. A separate regression reproduced cancelled completion being published after a delayed recovery-marker clear.

Application source `2ae6244` makes interruption persistent for that explicit attempt, checks it after Continue's asynchronous reads and before deferred provider admission, and checks again before publishing completion. Explicit fresh/Continue actions reset the state. Passive initial local preparation and the deliberately paused login path retain their prior behavior. In-flight durable saves/cleanup still settle under existing recovery rules; the fix neither clears user data nor enables background Sync.

Verification: the deferred Continue/optional-source regressions failed before the fix; the parent also reproduced the delayed-final-cleanup failure (`build/sync-background-fix/tail-red.log`). The complete host checkpoint passed TypeScript, lint, 1,410 mobile tests (2 skips), Python and fixture parity (`build/host-checks/20261026T142257Z-0fba904c`). Coverage includes explicit retry after cancellation, recovered and unrecovered flight paths, deferred source admission, optional jobs, final cleanup, paused login and existing durable-save/recovery guards. This host evidence does not establish the same timing race on an actual authenticated Android provider session.
